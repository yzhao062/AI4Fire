## Communication and Alerts + Data Retrieval and Tool Use

Neither category has a usable off-the-shelf dataset, and the reason differs. Communication and Alerts fails on evidence: the BEACON preprint (arXiv 2609.03301, 2026-09-03) releases no code, no data and no quantitative evaluation, its Watch Duty feed is closed by a terms-of-service clause that prohibits automated access and derivative works, and the one public multilingual crisis corpus with an urgency scheme (UrgencyScenarios) is unreleased and contains no fire. Data Retrieval and Tool Use fails only on assembly: five free, documented, license-clean fire APIs and databases were verified working during this check, including a 2.3-million-record wildfire SQLite database that may be used "without additional permissions or fees" and a NIFC perimeter service whose 2026 year-to-date layer held 7,027 post-cutoff fires, so gold answers can be computed by a reference program instead of annotated. The practical order is to build the tool-use task first, reuse its NIFC and NWS harvest as the factual spine of an evacuation-guidance task, and treat the multilingual layer as the one place where paid human reference translation is unavoidable.

### Multilingual wildfire evacuation guidance dialog

- Category and domain: Communication and Alerts, wildfire
- Verdict: **not-feasible-now**
- Data: None found as a released dataset. BEACON (kulkarni2026beacon, arXiv 2609.03301) is a system demonstration that ingests third-party live feeds: Watch Duty (fire perimeters, evacuation order status, shelters), NOAA HRRR (for the Hourly Wildfire Potential index), Overpass API (points of interest), OpenRouteService (polygon-avoidant routing), Mapbox, Qdrant and BigQuery. None of these is a benchmark dataset, and the paper releases nothing.
- Page: https://arxiv.org/abs/2609.03301
- Access: none found for the BEACON evaluation data. The underlying feeds split three ways. Watch Duty: effectively closed. Its terms of service state "You must not use any robot, spider, or other automatic device, process, or means to access the Platform for any purpose" and "You must not access or use for any commercial purposes any part of the Platform", and prohibit users from "reproduce, distribute, modify, create derivative works of" the material without prior written consent; the professional data feed routes through a "Contact Sales" path with no published pricing or self-serve registration. The single openly published Watch Duty layer is the Prescribed Burn Aggregation Service on ArcGIS Online (item 1784011a31104a45a584b26dbd23adfe, created 2024-12-10), which covers prescribed burns rather than wildfire perimeters or evacuation orders and carries a 14-day retention window, so it has no archive. NOAA: fully open. HRRR is on AWS Open Data with "AWS CLI Access (No AWS account required)" and an archive back to 2014 in GRIB2 and Zarr; the NWS API at api.weather.gov needs no key, only a User-Agent string. OpenRouteService: free after registering for an API key through a HeiGIT account, with a quota that "will be reset every 24 hours".
- License: The BEACON preprint itself is CC BY 4.0, but that covers the paper, not data it never released. Watch Duty: research use is not granted and redistribution of derived items is prohibited without written consent; the terms reference a Creative Commons Attribution-NonCommercial 4.0 International License for platform material, and the one public ArcGIS layer states "Commercial or for-profit use of this service is strictly prohibited without prior written consent from Sherwood Forestry Service, dba Watch Duty." NOAA NODD: "NOAA data disseminated through NODD are open to the public and can be used as desired", with attribution requested, no endorsement implied, and a requirement not to present modified data as unaltered NOAA data. NWS API: "All of the information presented via the API is intended to be open data, free to use for any purpose. As a public service of the United States Government, we do not charge any fees." Both NOAA paths allow research use and release of derived items; Watch Duty does not.
- Size: Zero released evaluation items. For the substitute sources: the NIFC WFIGS year-to-date perimeter layer returned {"count":7027} on 2026-09-15 under a definition query of attr_FireDiscoveryDateTime > timestamp '2026-01-01 04:00:00'; the historic perimeter view returned {"count":98168}; the WFIGS Incident Locations current layer carries 174-field incident records with a maxRecordCount of 2000 per request. The Iowa Environmental Mesonet NWS warning archive covers VTEC watch/warning/advisory products from 2005-11-12 (polygons from 2002-01-01, county-level from 1986-01-01) and includes "[FW] Red Flag".
- Reference answers: None. The BEACON paper is explicit that "The results below are qualitative observations of the end-to-end system behaviors": no metric, no test-case count, no ground truth, no baseline, no released evaluation set. It reports observations on Colorado fires from July to September 2025. There is nothing to score guidance against in the motivating work. Reference answers do exist for the factual substrate a guidance task would rest on, and they are machine-readable rather than annotated: NWS CAP alerts carry urgency (verified value "Expected"), severity ("Severe") and certainty ("Likely") alongside headline, description, instruction, areaDesc, effective and expires; the alert type list includes "Fire Warning", "Evacuation Immediate", "Red Flag Warning", "Fire Weather Watch" and "Extreme Fire Danger". NIFC incident attributes (IncidentName, IncidentSize, PercentContained, FireCause, FireDiscoveryDateTime, ContainmentDateTime, POOState, TotalIncidentPersonnel) are exact values that a reference program can look up.
- Dating and contamination: Excellent on the substitute sources, absent on the motivating work. The BEACON preprint was submitted 2026-09-03 and is under review for the IEEE SpatialConnect Workshop 2026, so it postdates most current model cutoffs but ships no items. NIFC perimeters and incident records carry FireDiscoveryDateTime, and the year-to-date layer is filtered to fires discovered after 2026-01-01, which is after the training cutoff of the models this benchmark would run; that is the cleanest contamination control found anywhere in this check. NWS alerts carry effective and expires timestamps and the IEM archive is indexed by issuance time. Watch Duty's one public layer has a 14-day retention window, so items built from it cannot be dated back beyond two weeks.
- Build route: Build it, from three verified public sources, and split the task so that the scorable part is separated from the part that needs human reference. (1) Factual spine: harvest the NIFC WFIGS services at https://services3.arcgis.com/T4QMspbfLg3qTGWY/arcgis/rest/services/WFIGS_Interagency_Perimeters_YearToDate/FeatureServer/0 and .../WFIGS_Incident_Locations_Current/FeatureServer/0 for 2026 fires. Gold answers come from a point-in-polygon test or an attribute lookup, so the label cost is near zero. (2) Official guidance text: harvest fire and evacuation CAP alerts from https://api.weather.gov/alerts (types verified at https://api.weather.gov/alerts/types) and, for historical coverage, from the free unregistered Iowa Environmental Mesonet archive at https://mesonet.agron.iastate.edu/request/gis/watchwarn.phtml. The official instruction field is the reference for what a resident should be told, and urgency, severity and certainty are the reference labels. (3) Routing, if it is kept in scope: OpenRouteService with a registered free key, within the published per-request restrictions at https://openrouteservice.org/restrictions/ (6,000 km maximum distance, 50 route waypoints, 3 alternatives, isochrones capped at 5 locations and 10 intervals, matrix capped at 3,500 origin-by-destination pairs). Drop Watch Duty entirely; its perimeters are sourced from NIFC in the first place, so harvesting NIFC gets the same geometry without the terms-of-service problem. The multilingual layer has no public gold: commission native-speaker reference translations for a small set (5 languages by 100 items is a realistic floor), or restrict scoring to facts that survive translation, which is the cheaper and more defensible option.
- Effort: High, and concentrated in one place. Two to four weeks of engineering for a 300 to 600 item English factual set: a snapshot harness that freezes API responses with a recorded fetch timestamp, a reference program that computes gold answers, question templating, and a human spot-check pass. The multilingual half is the real cost and it is money rather than time: professional translation of reference guidance into each target language, plus a bilingual adequacy check. Budget that separately before committing the task to the paper.
- Automatic scoring: Three separate problems. First, evacuation guidance is open-ended prose, so only the checkable facts inside it (is this address inside an active perimeter, is it inside an alert polygon at time T, what is the containment percentage, what does the official instruction say to do) are deterministic; the advice itself needs an LLM-judge rubric or expert review, which is the choice already flagged in subsection 7.6. Second, every source is a live moving target: the NIFC current layers carry rolling definition queries, so a benchmark must pin a frozen snapshot and publish the fetch timestamp or scores will not reproduce. Third, the multilingual dimension breaks exact-match scoring, because a correct answer in Tagalog will not string-match an English gold; entity-level extraction plus back-translation checking is workable but adds a second model into the scoring loop, which the paper would then have to justify.
- Notes: The preprint caveat applies in its strongest form: arXiv 2609.03301 is a preprint under review whose data has not been released, and unlike most such cases there is no dataset to release, because the system consumes live third-party feeds rather than a corpus. A second BEACON record exists in the context pack (kulkarni2026beaconrs) describing the same system; the arXiv version is the one with a fetchable page. The Watch Duty blocker deserves to be stated plainly in the paper rather than left as an open todo in subsection 7.9: the feed BEACON depends on cannot legally be harvested for a public benchmark, and a reader checking the claim will find the same terms-of-service clause. Note also that the paper's own Hourly Wildfire Potential dependency traces to a peer-reviewed source (James et al. 2025, Weather and Forecasting 40(9):1805-1822, computed from the operational HRRR model), so the danger-assessment half of BEACON rests on open NOAA data even though the situational half does not.

### Crisis translation and urgency classification with fire content

- Category and domain: Communication and Alerts, both (the fire-bearing public corpora split between wildfire social media and a small structure-fire message subset)
- Verdict: **needs-work**
- Data: No corpus exists that is multilingual AND carries fire items AND carries urgency labels. Four public corpora each have two of the three: HumAID (English, wildfire, humanitarian labels); CrisisMMD (English, 2017 California wildfires, damage-severity and humanitarian labels); Multilingual Disaster Response Messages (multilingual, an explicit fire category, no urgency scale); WildFireCan-MMD (English, Canadian wildfires 2022-2024, twelve themes). The motivating work's own data does not help: ticona2026translation uses TICO-19 (CC0, 3,071 sentences, 36 languages, COVID-19 only) and UrgencyScenarios (100 curated English sentences on a 6-level scale of Critical, High, Medium, Low, Very Low, Not Urgent, machine-translated with NLLB-200 into 29 languages for 3,000 items), and neither contains fire.
- Page: https://github.com/rmunro/disaster_response_messages
- Access: public download for three of the four, with a licensing catch on two. Multilingual Disaster Response Messages: direct download of three CSVs from GitHub, no registration. HumAID: direct download from https://crisisnlp.qcri.org/humaid_dataset.html and a mirror at https://huggingface.co/datasets/QCRI/HumAID-all that ships full tweet_text. CrisisMMD: direct download of a ~1.8 GB tarball from CrisisNLP. WildFireCan-MMD: GitHub, but only identifiers, since the paper states "The full set of labeled data (containing the tweet IDs and labels), as well as the experimental code, is available on Github", so items must be rehydrated through the X API, which is now a paid and restricted path. CrisisFACTS gold-standard facts for the 2022 events are public JSON on GitHub, but the full data streams need free registration with TREC. UrgencyScenarios: none found; the ISCRAM proceedings page states "Download data is not yet available" and the arXiv HTML carries no data or code availability statement.
- License: Multilingual Disaster Response Messages: CC BY 4.0, confirmed in the repository LICENSE file. This is the only fire-bearing multilingual source found whose license plainly permits research use and redistribution of derived benchmark items, subject to attribution. HumAID: the Hugging Face mirror declares cc-by-nc-sa-4.0, which would permit non-commercial derived items with share-alike, but the CrisisNLP terms of use that gate the primary distribution conflict with it, requiring that you "use the data only for research on humanitarian computing", that "You will keep the contents of these dataset(s) confidential (you can always share the tweet-ids)", and that derived datasets be deleted on request or on completion of the research. Those two cannot both be honored while publishing a derived benchmark, and the conflict has to be settled with QCRI in writing before release. CrisisMMD sits under the same CrisisNLP terms. WildFireCan-MMD: CC BY 4.0. TICO-19: CC0. NWS CAP alerts (the build-route source): "open data, free to use for any purpose" with no fees.
- Size: Measured directly, not quoted. Multilingual Disaster Response Messages: 23,850 rows total (19,116 train, 2,337 validation, 2,397 test), of which exactly 266 carry fire=1 (224, 31, 11 across the splits), and of those only 38 have a non-empty original untranslated field. The fire rows split 225 news to 41 direct messages. Original languages are Haitian Creole (2010 Haiti earthquake) and Urdu (2010 Pakistan floods), so the usable multilingual fire subset is 38 items and most of them describe structure fires in Port-au-Prince. HumAID wildfire subsets, from the event-wise table: 2016 Canada Wildfires 2,259 (collected 2016/05/06 to 2016/05/27), 2018 Greece Wildfires 1,526 (2018/07/24 to 2018/08/18), 2018 California Wildfires 7,444 (2018/11/10 to 2018/12/07), for 11,229 labeled wildfire tweets out of 77,196 overall. CrisisMMD: 16,097 tweets and 18,126 images across 7 events, one of which is the 2017 California wildfires. WildFireCan-MMD: 4,688 labeled image-text pairs plus 46,279 unlabeled posts spanning 2018-2024.
- Reference answers: Categorical labels exist, but none of them is urgency on a fire item in a non-English language. Multilingual Disaster Response Messages: 38 binary category columns, with fire documented as "whether the message is related to fire, including house fires and bush/forest fires", plus request, offer, aid_related, search_and_rescue and direct_report, which together approximate but do not equal an urgency scale. HumAID: 11 single-label humanitarian classes, of which "Requests or urgent needs", "Caution and advice" and "Displaced people and evacuations" are the urgency-adjacent ones. CrisisMMD: informativeness, 8 humanitarian categories, and a three-level damage severity. WildFireCan-MMD: twelve themes including Warnings & Status Updates and Evacuees. CrisisFACTS: gold-standard fact nuggets in JSON. The cleanest reference labels for this exact task are not in any of these: NWS CAP alerts carry a machine-readable urgency field (Immediate, Expected, Future, Past, Unknown) assigned by the issuing office, verified alongside severity and certainty on a live Red Flag Warning.
- Dating and contamination: Poor on everything that exists, good on the build route. Multilingual Disaster Response Messages covers 2010-2012 events and has been on GitHub, on Kaggle and inside a widely taken Udacity nanodegree for years, which is close to a worst case for contamination. HumAID covers 2016-2019 events and has been public since its ICWSM 2021 paper. CrisisMMD covers 2017. CrisisFACTS wildfire events are Lilac 2017, Cranston 2018, Holy 2018, Saddleridge 2019 and Kincade 2019. WildFireCan-MMD is the freshest at 2022-2024, but its items are only recoverable through a paid API. By contrast, NWS CAP alerts are timestamped at issuance and 2026 alerts postdate current model cutoffs, so items harvested from 2026 carry low contamination risk and can be dated to the second.
- Build route: Build it from NWS CAP alerts, which solve the label problem and the license problem at once. Harvest fire-related alerts from https://api.weather.gov/alerts, restricted to the five verified fire and evacuation event types (Red Flag Warning, Fire Weather Watch, Fire Warning, Extreme Fire Danger, Evacuation Immediate), with historical depth from the free unregistered Iowa Environmental Mesonet archive at https://mesonet.agron.iastate.edu/request/gis/watchwarn.phtml, which covers VTEC products from 2005-11-12 and explicitly lists [FW] Red Flag. Each alert arrives with an official urgency, severity and certainty plus headline, description and instruction, so the urgency label is authored by the issuing meteorologist rather than by us. Translate each item into the target languages with an open model (NLLB-200, the same family ticona2026translation used) and ask the model under test to assign urgency to the translated item; score against the CAP urgency of the English original. That measures exactly the asymmetry the motivating work found, needs no human reference translation at all, and stays inside a public-domain source. Two guards are required: strip the event name and any product boilerplate from the item, or the model will shortcut by recognizing "Red Flag Warning" instead of reading the text; and hold out a human-verified sample to confirm the machine translation did not itself destroy the urgency signal, since otherwise the benchmark measures NLLB-200 rather than the model under test. If translation quality itself is to be scored (chrF or COMET), that does need reference translations and becomes a paid step. For a fire-message set with no license friction at all, the 266 fire rows of the CC BY 4.0 Multilingual Disaster Response Messages corpus can seed a small structure-fire slice, but 38 of them being genuinely multilingual makes it a supplement rather than a foundation.
- Effort: Low to moderate, and much cheaper than item 1. A few days of scripting to harvest, filter and normalize CAP alerts and to run NLLB-200 translation into a chosen language set. One to two weeks for question construction, boilerplate stripping and a human verification pass on a sample of translated items. The only open-ended cost appears if reference translations are commissioned for translation-quality scoring, which is optional under the design above.
- Automatic scoring: Four things make it hard. CAP urgency is a coarse five-value field that is largely determined by product type, so accuracy will be high and compressed unless items are stratified and the event name is removed; without that the task tests pattern recognition on a template. The urgency labels are also correlated with the issuing office's local conventions rather than with the message content alone, which weakens them as a ground truth for what a reader should feel. Cross-language exact match fails for free-text outputs, so the model must be constrained to emit one of the five labels, which in turn narrows what the task measures. And if the corpora route is taken instead, the CrisisNLP confidentiality clause means derived items cannot be published, so the benchmark would be unreproducible by a reader, which is the one failure this paper cannot accept given the TMLR audience.
- Notes: The table's current framing of ticona2026translation as "adjacent work with no fire task" is correct and the check makes it stronger: not only is there no fire task, the paper's new dataset is not released and its base corpus is CC0 COVID-19 text, so nothing can be inherited. Two corrections the paper should absorb. First, the row's data-access cell should stop saying "fire items need a new source; access unchecked" and say instead that the fire-bearing public corpora are English-only, that the one multilingual fire subset found is 38 messages, and that the license path runs through CAP alerts rather than through social media. Second, the CrisisNLP confidentiality clause is a redistribution blocker on the two largest wildfire tweet corpora and belongs in subsection 7.7 as a licensing finding, not left implicit. On multilingual alerting specifically: NOAA does run an automated Spanish and Chinese translation service, but a live query of api.weather.gov returned alerts tagged "language": "en-US" with no Spanish counterpart, so there is no aligned bilingual machine-readable feed to harvest today; the NOAA news release that would document the API roadmap returned HTTP 403 on two attempts and is listed in failed_fetches.

### Agents that query fire databases, APIs, or tools

- Category and domain: Data Retrieval and Tool Use, both, but asymmetrically: wildfire is well served and structure fire is not
- Verdict: **needs-work**
- Data: No fire tool-use benchmark exists; a search for one surfaced only FireBench (arXiv 2603.04857), which is enterprise instruction-following and has nothing to do with fire. What does exist is a set of stable public fire data services that a benchmark can be built on. Verified working during this check: (1) NASA FIRMS Area API, satellite active-fire detections; (2) NIFC WFIGS ArcGIS REST services, authoritative US wildland fire perimeters and incident records; (3) NWS API at api.weather.gov, fire weather and evacuation alerts; (4) OpenFEMA API, federal disaster and NFIRS holdings; (5) FPA-FOD (Short 2022, RDS-2013-0009.6), a spatial wildfire occurrence database shipped as SQLite. For structure fire: the NFIRS Public Data Release as bulk files, and NFPA codes, which are not usable.
- Page: https://www.fs.usda.gov/rds/archive/catalog/RDS-2013-0009.6
- Access: public download or free API for all five wildfire sources. FPA-FOD: direct download from the Forest Service Research Data Archive, no registration, in ACCDB, GDB, GPKG and SQLite. FIRMS: free MAP_KEY issued by email, with the documented limit "MAP_KEY limit is 5000 transactions / 10-minute interval" and an invitation to contact FIRMS for more. NIFC WFIGS: no key, no registration, full ArcGIS query support including statistics and pagination. NWS API: no key, User-Agent string required. OpenFEMA: "Use of the service is free and does not require a subscription or API key", OData query syntax, default 1,000 records and maximum 10,000 per request. Structure fire is the weak side: the NFIRS Public Data Release is a free bulk download through OpenFEMA rather than a query API, and NFPA codes are behind a registration-gated read-only viewer where documents "cannot be downloaded or printed" and text cannot be copied, with no API and no bulk access, which rules out a scored code-retrieval tool task on NFPA text.
- License: Clean for research use and derived items on the wildfire side. FPA-FOD: the data "were collected using funding from the U.S. Government and can be used without additional permissions or fees", with citation required (Short, Karen C. 2022, 6th Edition, https://doi.org/10.2737/RDS-2013-0009.6). NASA FIRMS: NASA Earthdata policy states that data from a NASA-led mission are licensed CC0 unless marked otherwise, free and open, citation strongly urged, with the requested acknowledgement naming LANCE FIRMS and ESDIS. NIFC WFIGS: the authoritative NIFC_Authoritative item carries no open-license grant and no restriction either, only a liability disclaimer, "The National Interagency Fire Center shall not be held liable for improper or incorrect use of the data described and/or contained herein." A Data Basin mirror asserts CC BY 3.0; that is a mirror and should not be cited as the license. NWS API: open data, free for any purpose. OpenFEMA: reuse permitted, with a required citation naming the endpoint, version and access time plus the disclaimer "This product uses the Federal Emergency Management Agency's OpenFEMA API, but is not endorsed by FEMA", and a prohibition on reidentifying individuals.
- Size: FPA-FOD: "2.3 million geo-referenced wildfire records, representing a total of 180 million acres burned", 1992-2020, SQLite build 213.96 MB (ACCDB 172.18 MB, GDB 136.26 MB, GPKG 210.98 MB). NIFC: the year-to-date 2026 perimeter layer returned {"count":7027} and the all-years historic perimeter view returned {"count":98168}; the current perimeter layer exposes 174 fields with maxRecordCount 2000. FIRMS: MODIS at roughly 1 km and VIIRS at 375 m nominal, with archives running from November 2000 (Terra), July 2002 (Aqua), 2012-01-20 (VIIRS SNPP), 2020-01-01 (NOAA-20) and 2024-01-17 (NOAA-21). NFIRS Public Data Release: 1980 through 2025, zipped CSV for 2012 onward and dBASE before that, with "compressed zip file sizes vary from 132 MB and can range up to 822MB" per year, and GeoPackage geocoded versions for 2020-2025.
- Reference answers: This is the category's strongest property: gold answers are computed, not annotated. A reference program runs the intended query against a frozen snapshot (an FPA-FOD SQLite file, or a dated dump of WFIGS and FIRMS responses) and its output is the label, so annotation cost is near zero and the answer is exact for numeric and categorical questions. The NIFC incident schema supplies the value types that make this work: IncidentName, IncidentSize, FinalAcres, DiscoveryAcres, FireDiscoveryDateTime, ContainmentDateTime, ControlDateTime, FireOutDateTime, PercentContained, FireCause with FireCauseGeneral and FireCauseSpecific, POOState, POOCounty, GACC, EstimatedCostToDate, EstimatedFinalCost, TotalIncidentPersonnel and IrwinID. FPA-FOD supports compositional aggregates over cause, size class, state and year that no model can have memorized. FIRMS supports counting and thresholding detections within a bounding box and date range.
- Dating and contamination: The best of the three items. NIFC's year-to-date layer is filtered to fires discovered after 2026-01-01 and held 7,027 perimeters on 2026-09-15, all of which postdate current model training cutoffs, which makes it the single cleanest contamination-controlled fire source found in this whole check. FIRMS near-real-time detections are dated to the satellite overpass and can be pulled for any post-cutoff window. FPA-FOD is the opposite case: 1992-2020 data that has been public since the first edition in 2013 and in its 6th edition since 2022, so individual headline-fire facts may well be memorized, though compositional aggregates over it are not. NFIRS annual releases are dated by incident year. The practical recommendation is to draw contamination-controlled items from NIFC 2026 and FIRMS 2026, and use FPA-FOD for aggregate queries where memorization is not a plausible shortcut.
- Build route: not needed as a rescue, but the task itself must be constructed, since no fire tool-use benchmark exists. Design: freeze a snapshot of each source with a recorded fetch timestamp; write a reference program that answers each question against that snapshot; give the agent either live or replayed tool access to the same source; compare its answer to the reference program's output. Concretely, the FPA-FOD SQLite file at https://www.fs.usda.gov/rds/archive/catalog/RDS-2013-0009.6 is the best single starting point because it is one self-contained file that needs no network at run time, which removes the flakiness that usually sinks tool-use benchmarks. Layer a live tier on top of it using the NIFC services at https://services3.arcgis.com/T4QMspbfLg3qTGWY/arcgis/rest/services/ and the FIRMS Area API at https://firms.modaps.eosdis.nasa.gov/api/area/ to test whether an agent can compose a correct query against a documented but unfamiliar REST interface. Keep OpenFEMA and the NWS API as a second tool per question, so the benchmark measures tool selection and not just query writing. For a structure-fire arm, the only viable source is the NFIRS Public Data Release loaded into a local database; NFPA and ICC code text cannot support a scored task because free access is read-only with copying disabled.
- Effort: Moderate, and the lowest-risk of the three. Roughly one week for a snapshot and replay harness plus the reference query program over FPA-FOD; one week for question templating across difficulty tiers (single lookup, filtered aggregate, multi-source join) and a human spot-check of a sample; a few days to wire the live NIFC and FIRMS tier and to handle key management. A 400 to 800 item set is realistic inside a month for one engineer.
- Automatic scoring: Five concrete hazards. Live endpoints drift, since the NIFC current layers carry rolling definition queries (the current perimeter layer is filtered to FireDiscoveryDate after 2025-12-01) and FIRMS replaces near-real-time records with standard-processing records, so an unpinned benchmark will not reproduce. Secrets are per-runner: a FIRMS MAP_KEY and an NWS User-Agent must be supplied by whoever runs the evaluation, which complicates a public leaderboard. Network failure must be distinguished from a wrong answer, or transient outages become model errors. Numeric answers need a tolerance policy, because acreage and cost fields are revised upstream and an agent that queries a moment later gets a slightly different truth. And partial credit over a multi-step tool trajectory needs an explicit rubric, since an agent can reach the right number through a wrong path or the wrong number through a sound one; scoring only the final answer hides the distinction the category exists to measure. Paging is a sixth, smaller trap: maxRecordCount is 2000 on the NIFC layers and 10,000 on OpenFEMA, so a correct aggregate requires the agent to page or to push the aggregation server-side.
- Notes: Two facts that should change how the paper writes this row. First, the row currently reads "Which databases, APIs, or tools? Access unchecked" with no motivating work; the answer is now concrete and the table cell can name FPA-FOD, NIFC WFIGS, NASA FIRMS, the NWS API and OpenFEMA, all with fetchable license statements. Second, this is the only one of the three items where the reference-answer problem is solved rather than deferred, because the gold answer is a computed value from a public snapshot; that makes it the strongest candidate in this group for a task that actually ships. Two cautions for accuracy. NIFC's authoritative item states no license, only a liability disclaimer, so the paper should describe it as an unrestricted US interagency product rather than assert a Creative Commons license that only a mirror claims. And NFIRS is being retired: USFA guidance indicates the system is sunsetting in early 2026 with the 2025 reporting deadline set at 2026-01-31, and the FEMA data page carries the warning that "Using raw NFIRS data as a count of fires and associated deaths, injuries and dollar loss is NOT a proper use of these datasets", so a structure-fire arm built on NFIRS needs both a statement about the successor system and a question design that avoids raw counts.

### Quantitative fire radiative power (FRP) forecasting: the model is given a day's fire-weather and vegetation drivers for a located grid cell as text and must return a numeric next-step FRP value, scored against the observed FRP.

- Category and domain: Forecasting and Prediction, wildfire
- Verdict: **needs-work**
- Data: No released dataset behind the motivating work. ramesh2025wildfiregpt used a table of 61 features and 619,373 rows that it says was "primarily sourced from the NASA Fire Energetics and Emissions Research platfrom (Davies et al. 2008), which provides detailed MODIS-based fire-related data, including Fire Radiative Power (FRP) values", trained on 2020 data and evaluated on a separate July 2021 set. That citation is internally inconsistent: Davies et al. 2008 is the FIRMS paper ("Fire information for resource management system: archiving and distributing MODIS active fire data"), not a FEER paper, and the FEER site itself no longer resolves. The paper names no spatial resolution, no study region, and no repository. The buildable substitute is the NASA FIRMS active-fire archive: MODIS Collection 6.1 at 1 km (center of a 1 km fire pixel) and VIIRS at 375 m (center of a nominal 375 m fire pixel), both of which carry an FRP attribute described as "the pixel-integrated fire radiative power in MW (megawatts)".
- Page: https://firms.modaps.eosdis.nasa.gov/download/
- Access: The paper's own table: none found. There is no data availability statement, no repository link, and no supplementary file; the article's back matter carries only Funding, Conflict of Interest, and Ethical approval sections. FIRMS: public but behind a light gate. Archive download for data older than 7 days requires "Authentication through Earthdata or Email", and the Area API requires a MAP_KEY, which the page describes as "sign up for free MAP_KEY using your email. The key will be sent to your email", capped at "5000 transactions / 10-minute interval". Formats are CSV, SHP, and JSON.
- License: The article is CC BY 4.0 (Crossref records https://creativecommons.org/licenses/by/4.0 for both the TDM and VOR versions, effective 2025-05-28), but that covers the text and not an unreleased table. FIRMS data fall under NASA's Earth Science Data and Information Policy, which commits to "the full and open sharing of Earth science data obtained from NASA Earth observing platforms" with "no period of exclusive access". NASA asks for the acknowledgement "We acknowledge the use of data and/or imagery from NASA's Fire Information for Resource Management System" when data are passed to third parties. Research use and redistribution of derived questions are both allowed; no clause restricts derivative works.
- Size: Paper's table (unreleased): 61 features, 619,373 rows, with a 74,550-row subset used for model selection. FIRMS archive (usable): MODIS Collection 6.1 from 2000-11-01 to present, VIIRS S-NPP 375 m from 2012-01-20, VIIRS NOAA-20 from 2018-04-01, VIIRS NOAA-21 from 2024-01-17, LANDSAT 30 m from 2022-06-20. Per-detection rows, so item count is a sampling decision rather than a fixed size.
- Reference answers: Yes, once we build them. Each FIRMS detection row is a reference answer: a scalar FRP in megawatts attached to a latitude, longitude, acquisition date, and acquisition time in UTC. Scoring follows what the motivating paper reports: MAE, MSE, and R-squared (TabNet reached MAE 0.055, MSE 0.011, R-squared 0.405; WildfireGPT reached MAE 14.849, MSE 3.432, R-squared 0). The paper also describes exactly how its prompts were made, which is reusable: "to construct a prompt for WildfireGPT, we flatten all the columns from our training data and merge them into one coherent sentence", and it shows one worked item ("Predicted FRP = 650 w/m2 (true FRP = 6.77 w/m2)").
- Dating and contamination: Item-level dating is exact. Every FIRMS row carries acq_date and an acq_time "of acquisition/overpass of the satellite (in UTC)", so a post-cutoff window can be cut to the minute. Near-real-time rows are replaced by standard science quality with roughly a 5-month lag, so a stable test window is available about five months after the fact. Contamination picture: the motivating article has been open access since 2025-05-28, so its specific numbers and its example prompt are inside a 2026 model's likely training window and should not be reused verbatim. Items cut fresh from a 2026 FIRMS window carry low contamination risk, because the FRP values are numeric rows rather than prose.
- Build route: Pull a dated window from the FIRMS archive (https://firms.modaps.eosdis.nasa.gov/download/) or the Area API (https://firms.modaps.eosdis.nasa.gov/api/area/) after requesting a free MAP_KEY (https://firms.modaps.eosdis.nasa.gov/api/map_key/); the FRP column and units are documented at https://www.earthdata.nasa.gov/data/tools/firms/active-fire-data-attributes-modis-viirs. Join per-cell meteorological drivers from NASA POWER (https://power.larc.nasa.gov/docs/services/api/) for temperature, humidity, wind, and pressure, which is the same climate source FireScope-Bench uses, and derive vapor pressure deficit from temperature and humidity. Build lagged FRP features by binning detections to a grid and taking the previous 1 to 7 days, mirroring the paper's FRP_1_days_ago style features. Then flatten each row into one sentence, as the paper describes, and hold out a window after every evaluated model's cutoff.
- Effort: Two to three weeks of one person's work. Most of it is the spatial and temporal join (gridding point detections, aligning POWER cells to FIRMS pixels, building the lag features) and the holdout cut. The FIRMS pull itself is an afternoon. Add a few days for a non-LLM baseline, since the paper's headline claim only means something beside TabNet or gradient boosting on the same rows.
- Automatic scoring: Three things make it awkward. First, units: the paper reports predictions in W/m2 while FIRMS reports FRP in MW, so an item must fix the unit in the prompt or the error metric is meaningless. Second, FRP is heavily right-skewed, so a raw MAE rewards a model that always answers near the median and R-squared can sit at 0 for a model that is not actually random; report both, plus a constant-median baseline, or score on log FRP. Third, parsing: a chat model answers with a sentence, a range, or a refusal, so the harness needs a strict numeric extraction rule and an explicit non-answer bucket rather than scoring a failed parse as a large error.
- Notes: The outline's Section 7.9 bullet "NASA fire radiative power datasets, as used by ramesh2025wildfiregpt" cannot be written as a single citable source, because the paper points at two different things at once. The text names the NASA Fire Energetics and Emissions Research platform, whose site returns 404 at every path checked, while the inline citation is the FIRMS archiving paper. If the paper is cited in Section 7.9, say that the source is described as MODIS-based FRP from a NASA platform and that the table is not released, rather than naming a product the paper never names. On the positive side, this is the group's weakest measured capability and also the task with the cleanest build route: FIRMS gives dated, numeric, post-cutoff items with a documented unit, which is exactly what a contamination-controlled forecasting task needs.

### Wildfire risk sub-criteria scoring against expert rankings: the model assigns importance weights to 16 wildfire risk sub-criteria under an AHP-style hierarchy, and its ranking is correlated against a published expert baseline.

- Category and domain: Forecasting and Prediction, wildfire
- Verdict: **needs-work**
- Data: The materials behind cheng2026retrieval (Fire 2026, 9, 143). Both halves asked about are released, in three places. (1) The 16 sub-criteria are named in the article body: species composition, development stage, stand crown closure, aspect, slope, elevation, topographic wetness index, distance from settlement, distance from agriculture, distance from road, distance from river, population density, temperature, precipitation, wind speed, solar radiation, grouped under four primary criteria (forest structure, topography, environment, climate). (3) Supplementary Materials S1 to S5 plus "Data S1: Experimental data" are attached to the article. - Access: Public download, no registration. The repository is public and holds three items: Prompt.txt (the prompts for all four strategies), an "MDS output/" folder, and "experiment data-rank.txt" (the ranking results for all experiments). The supplementary files sit at the article's /s1 path under the journal.
- License: Split, and this is the problem. The article is CC BY 4.0: Crossref records https://creativecommons.org/licenses/by/4.0/ for the VOR, and the PDF carries "Copyright: 2026 by the authors. So the ranking file is readable but not cleanly redistributable, and a derived item built from it should be sourced to the article and its supplement instead, or the authors should be asked to add a license.
- Size: 16 items. That is the whole task. Five LLMs were evaluated (ChatGPT-4o, Gemini-2.0, Baichuan-3, Kimi-1.5, ChatGLM-4) across four strategies (DLS, MDS, FDP, IGP), all through their official web platforms, with one final output per model per strategy and no repeated runs except for MDS.
- Reference answers: Yes, and in a directly scorable form: a 16-element integer rank vector. The paper's own metrics are Pearson's R, Spearman's rho, and Kendall's tau against the expert baseline, reporting DLS at R = 0.009 +/- 0.070, MDS at R = 0.181, FDP at R = 0.081 +/- 0.189, and IGP at R = 0.598 +/- 0.065. Scoring a new model is a few lines of code.
- Dating and contamination: The article is dated precisely: received 2026-02-03, revised 2026-03-20, accepted 2026-03-24, published 2026-03-26. The repository was accessed by the authors on 2026-03-09. Contamination risk is high and structural rather than incidental: the expert baseline is the reported weight table of Sivrikaya and Kucuk 2022, which has been in the literature since 2022, so a 2026 model may reproduce that ranking from memory of the source paper rather than from reasoning about wildfire risk. That is a plausible alternative explanation for any high correlation and has to be tested, not assumed away.
- Build route: not needed for reuse, but a contamination-clean version would need a new baseline. Build it by taking a different published AHP wildfire risk study with a full expert weight table that postdates the model cutoffs, or by running a small expert elicitation of our own; the paper itself concedes the limitation, stating that "the expert baseline used in this study was derived from a single published source" and that "If a different but equally valid expert-derived study were adopted as the benchmark, the comparative outcomes might change accordingly."
- Effort: Two to three days to reproduce the task exactly as published, because the criteria, the prompts, and the reference vector are all in hand. Two to four weeks if a fresh expert baseline is needed, most of it recruitment and elicitation rather than engineering.
- Automatic scoring: The scoring itself is trivial; the statistics are the hard part. A correlation over 16 items has a very wide confidence interval, so the gap between R = 0.009 and R = 0.598 is real while small differences between models are not interpretable. There is only one output per model per strategy in the published run, so nothing measures run-to-run variance, and a chat model's ranking of 16 abstract criteria is known to move between samples. Any reuse should run each model many times and report the spread. A second issue: the models were accessed through their hosted web interfaces, and the paper says token length and platform-side context handling "were not systematically archived", so the published numbers are not strictly reproducible through an API.
- Notes: Section 7.6's "Correlation with Expert Rankings" metric and Section 7.4's "Retrieval Grounding" condition both rest on this one work, and the underlying task is 16 items scored against one 2022 paper's weight table. That is worth stating plainly in the paper rather than citing R = 0.598 as if it came from a benchmark. Three concrete things to fix if the task is adopted: give it more than 16 items, run each model repeatedly, and swap in a post-cutoff expert baseline. Access is the easy part here; the statistical power and the contamination channel are the real blockers. Also worth noting for Section 7.9: the MDPI article page returns 403 to automated fetches, so a reader checking this claim should be pointed at the DOI and the publisher PDF mirror.

The paper says "we produce a ground truth annotation" without describing how the annotations were made or validated, and the reported 50% for IC-EO against 0% for GPT-4o and LLaVA comes from the 12-question subset. The usable public source, and the one IC-EO's own tool-level evaluation used, is HLS Burn Scars: 804 scenes of Harmonized Landsat and Sentinel-2 v1.4 imagery with human-curated binary burn masks, on which IC-EO's segmentation tool reports 87.5 IoU for burned areas.
- Page: https://huggingface.co/datasets/ibm-nasa-geospatial/hls_burn_scars
- Access: IC-EO's 12 questions: none found. The arXiv page lists no code or dataset URL, and the paper carries no data availability or code availability statement. A request to the authors is the only route, and the paper is a preprint (submitted 2026-01-27, cs.CV and cs.AI) with no published venue named. HLS Burn Scars: public download from Hugging Face, no gating and no terms-acceptance step observed.
- License: IC-EO: the arXiv posting is under the arXiv non-exclusive distribution license 1.0, which covers the paper and confers no rights to any data. HLS Burn Scars: cc-by-4.0, which allows research use and the release of derived questions with attribution; the card asks for citation of Phillips et al. 2023, DOI 10.57967/hf/0956.
- Size: IC-EO: 12 burn-scar questions plus 12 object-presence questions. HLS Burn Scars: 2.65 GB, 1,068 rows covering 804 scenes of 512x512 pixels, split randomly two thirds training and one third validation (roughly 536 and 268).
- Reference answers: Not for IC-EO. Twelve items with an undescribed annotation procedure will not support a claim a TMLR reader can check, and 50% on 12 items is 6 correct answers, which no confidence interval can separate from chance on a binary question. HLS Burn Scars does have reference answers, as pixel masks with three values: 1 for burn scar, 0 for not burned, and -1 for missing data, with a class balance of roughly 11% burn scar, 88% not burned, and 1% no data. Those masks score a segmentation model exactly, and they can be reduced to a text-answerable reference (burned-area fraction of a scene, a burned-or-not call on a tile, or an ordering of scenes by burn extent).
- Dating and contamination: IC-EO items: undatable, since they are not released and the paper does not say which scenes they came from. HLS Burn Scars: scenes are drawn from HLS v1.4 imagery over the contiguous United States for 2018 to 2021, so each scene is datable to its acquisition. The dataset has been public on Hugging Face since 2023 (its citation DOI is a 2023 record), so contamination risk for a 2026 model is meaningful on the scene identities and the published leaderboard numbers, though the masks themselves are raster values rather than text. Both windows sit far before any 2026 model's cutoff, so this route cannot supply a post-cutoff holdout on its own.
- Build route: Build from HLS Burn Scars (https://huggingface.co/datasets/ibm-nasa-geospatial/hls_burn_scars), CC BY 4.0, 804 labeled scenes. Reduce each mask to a text-answerable reference: the burned fraction of the scene as a percentage, a binary burn-present call on sub-tiles, or a rank ordering of a small set of scenes by burned area. Render the six HLS bands to a visualization for the VLM condition and expose the same scene to a code-writing agent for the tool-grounded condition, which reproduces the comparison IC-EO actually cared about (a code-generating agent against a bare VLM) without depending on IC-EO's unreleased items. For a post-cutoff holdout, cut new scenes from the same HLS archive for 2026 fire seasons and label them against MTBS, though that adds the annotation work HLS Burn Scars already did for 2018 to 2021.
- Effort: Two to three weeks. The dataset download is small (2.65 GB), so the work is the item derivation, the band-to-image rendering, and the tool harness for the code-writing condition. Add several more weeks if a post-cutoff 2026 slice with new annotations is wanted.
- Automatic scoring: A burned-fraction question invites an unanchored number, so the item has to state the units and the denominator or the errors are not comparable. The 88% not-burned class balance means a binary per-tile item is trivially gamed by always answering "no", so the item pool must be balanced or the metric must be a per-class F1 rather than accuracy. The code-writing condition adds a second failure mode that is not a wrong answer: code that does not run. Score those separately, as IC-EO does with its agent-level check for "valid, hallucination-free code", or a model that writes nothing scores the same as a model that writes a wrong answer.
- Notes: The item as written in Table 7.3, reusing IC-EO's evaluation, is not feasible now: the data is not released, the annotation method is not described, and n=12 is too small to carry a claim. The verdict is needs-work only because HLS Burn Scars gives a clean, licensed, labeled substitute that IC-EO itself used at the tool level. Two consequences for the paper. Section 7.5's "Continuity Models" bullet cites GPT-4o and LLaVA from lahouel2026iceo so that new scores can be read beside earlier ones; that comparison cannot be made, because the 0% figure is on 12 unreleased items and nothing we build will be the same items. Section 7.9's "Earth observation imagery" line should name HLS Burn Scars rather than IC-EO's imagery, since the former is the only part with checkable terms.
- Evidence: https://arxiv.org/abs/2602.00117, https://arxiv.org/html/2602.00117v1, https://huggingface.co/datasets/ibm-nasa-geospatial/hls_burn_scars

### Next-day wildfire spread prediction from a multi-modal daily time series: given the recent daily observations for a fire, the model states whether specified cells burn on the following day.

- Category and domain: Forecasting and Prediction, wildfire
- Verdict: **needs-work**
- Data: WildfireSpreadTS (gerard2023wildfirespreadts), NeurIPS 2023 Datasets and Benchmarks Track. A multi-temporal, multi-modal remote-sensing dataset for predicting wildfire spread at 24-hour resolution, giving for each fire event a full time series of daily observations containing detected active fires plus fuel, topography, and weather variables.
- Page: https://zenodo.org/records/8006177
- Access: Public download, open access without login. Two files on Zenodo: WildfireSpreadTS.zip and WildfireSpreadTS_Documentation.pdf. The data loader, Lightning data module, and experiment code are at github.com/SebastianGer/WildfireSpreadTS under MIT.
- License: CC-BY-4.0 on the Zenodo record, with no access conditions or restrictions stated beyond the attribution CC BY requires. Research use and release of derived items are both allowed. The code is separately MIT licensed.
- Size: 48.4 GB (WildfireSpreadTS.zip), plus a 7.8 MB documentation PDF. 13,607 images across 607 fire events in the United States, January 2018 to October 2021.
- Reference answers: Yes. The label is the next day's active-fire mask, so a per-cell binary reference exists for every fire-day pair. That is already a scorable target for a raster model; a text-answerable version needs a reduction step (a burn-or-not call on a named cell, a count of newly burning cells in a window, or a direction-of-spread multiple choice), each of which keeps an exact reference.
- Dating and contamination: Item-level dating is exact, since the dataset is a daily time series and each fire event is bounded in time. The window is January 2018 to October 2021, and the dataset itself has been public on Zenodo since 2023-10-25 (version v1.0). That puts both the data and the NeurIPS paper's baselines inside a 2026 model's likely training window, so contamination risk on the published numbers is high. Risk on the per-cell labels is lower, because they are raster values rather than prose, but the 2018 to 2021 US fire events are extensively documented in text a model has read.
- Build route: not needed
- Effort: One to two weeks to derive text-answerable items and a scoring harness, dominated by the 48.4 GB download and by writing the cell-selection rule that avoids trivial items. The official data loader removes most of the parsing work.
- Automatic scoring: Class imbalance is the main hazard: on any given day most cells do not burn, so an accuracy metric rewards a model that always answers "no". Balance the item pool or score with per-class F1 and report a majority-class baseline. Naming a real fire in the prompt leaks the answer for well-documented events such as the 2020 California complexes, so fire identity must be stripped. There is no post-cutoff window available inside this dataset at all, which means it can support a capability measurement but not a contamination-controlled one.
- Notes: Access and license are the cleanest of any source in this group: one Zenodo record, CC BY 4.0, open, no login, with a documentation PDF and MIT-licensed loaders. The Section 7.9 entry can be marked checked. What stops it being ready is that it is a raster benchmark and a 2018 to 2021 one, so it gives no post-cutoff holdout. If the benchmark wants a spread-prediction task with contamination control, this dataset is the right structure and the wrong years; the fix is to rebuild the same item shape from a recent FIRMS window rather than to add years to this release.
- Evidence: https://zenodo.org/records/8006177

### Multi-task satellite image time-series wildfire tasks: active fire detection, daily burned-area mapping, and next-day progression prediction, posed as text-answerable questions over a described scene.

- Category and domain: Forecasting and Prediction, wildfire
- Verdict: **needs-work**
- Data: TS-SatFire (zhao2025tssatfire), Scientific Data 12, 1817 (2025). Surface reflectance image time series with auxiliary weather, topography, land cover, and fuel data, covering each wildfire's lifecycle, with active fire and burned area labels supported by manual quality assurance.
- Page: https://www.kaggle.com/datasets/z789456sx/ts-satfire
- Access: Public download through Kaggle, with an account. The article states "The TS-SatFire dataset is available on Kaggle, accessible via the link (https://www.kaggle.com/datasets/z789456sx/ts-satfire)". An unauthenticated request to the Kaggle download endpoint returns HTTP 404, which is how Kaggle hides a dataset from a signed-out caller, so a Kaggle account and an API token are needed in practice. The Kaggle public API returns the dataset metadata without authentication, which is how the license and size below were read. Benchmark models and the GeoTIFF processing scripts are at github.com/zhaoyutim/TS-SatFire.
- License: Creative Commons Attribution 4.0 International. The Kaggle record's licenseName is "Attribution 4.0 International (CC BY 4.0)" and the article carries the same. Research use and release of derived items are both allowed with attribution.
- Size: 76,314,754,827 bytes (about 76.3 GB) on Kaggle; the article states 71 GB. 3,552 surface reflectance images across 179 wildfire events. Last updated 2025-10-26; 71,131 downloads recorded.
- Reference answers: Yes, three label types, all pixel-level: active fire detection as pixel-wise binary classification (fire or non-fire), daily burned area mapping as pixel-wise binary segmentation (burned or unburned), and wildfire progression prediction as difference-based segmentation marking the newly burned pixels on the next day. Each scores exactly for a raster model. A text-answerable version needs the same reduction step as WildfireSpreadTS.
- Dating and contamination: January 2017 to October 2021 over the contiguous United States, with the active fire detection test set drawn from 2018 to 2022 across several continents, so every item is datable to its acquisition. The dataset went public on Kaggle by 2025-10-26 and the article was published 2025-11-19, with the arXiv preprint (2412.11555) dating to December 2024. Contamination risk on the published baselines is high for a 2026 model; risk on the pixel labels is lower for the same reason as the other raster sets.
- Build route: not needed
- Effort: Two weeks, similar to WildfireSpreadTS: the 76 GB download plus an item-derivation pass. The progression task is the one worth the effort here, because it is the only one of the three that is genuinely a forecast rather than a recognition task, and the survey's cross-cutting finding is about forecasting.
- Automatic scoring: Same imbalance problem as every pixel-level fire label, and a sharper one for progression, where the newly burned pixels on a given day are a small fraction of an already small burned area. The multi-continent active fire test split is the useful out-of-region holdout in this dataset and should be reported apart from the CONUS results rather than pooled.
- Notes: License and size are confirmed from the Kaggle public API rather than from the dataset page, which did not return a readable body; record that in the paper if the size is quoted, since the article says 71 GB and the API reports 76.3 GB (compressed against uncompressed is the likely explanation, but it is not stated anywhere I could fetch). The Kaggle hosting is the one access caveat worth a sentence in Section 7.9: it is a public dataset, but reproducing a download needs a Kaggle account, which is a heavier gate than a Zenodo record.

### Short-term wildfire danger forecasting: given the recent daily values of the fire drivers for a 1 km Mediterranean cell, the model states whether a fire ignites there, scored against the Mesogeos Track A binary label on a 2021 to 2022 time holdout.

- Category and domain: Forecasting and Prediction, wildfire
- Verdict: **needs-work**
- Data: Mesogeos (kondylatos2023mesogeos), NeurIPS 2023 Datasets and Benchmarks Track. - Access: Public download, no registration. The Zenodo DOI 10.5281/zenodo.7473331 resolves to the code archive (Orion-AI-Lab/mesogeos-v1.2.zip, 12.0 MB, DOI 10.5281/zenodo.8036851) rather than to the datacube, so the Drive folder is the actual data host. Record that distinction: a reader following the Zenodo DOI expecting 648 GB of data will get a 12 MB source zip.

- Size: The datacube "occupies a storage space of 648 GB" under default Zarr compression, and loading it needs about 3.2 TB of memory at 32-bit floats. The extracted ML tracks are far smaller and are the part worth downloading. Track A: 25,722 samples (8,574 positive, 17,148 negative), split 19,353 train (6,451 positive, 12,902 negative), 2,262 validation (754 / 1,508), and 4,107 test (1,369 / 2,738). Track B: 64 km x 64 km patches centered on each ignition point. Coverage is 2006-04-01 to 2022-09-29 over the Mediterranean (-10.72 to 36.74 E, 30.07 to 47.7 N).
- Reference answers: Yes, and this is the best-shaped reference in the group. Track A is already a binary classification label per sample, with published metrics and baselines (LSTM, a Transformer encoder, and a Gated Transformer Network), and it ships with a documented split. A text-answerable item is a direct rewrite: put the sample's driver values into a sentence and ask for a fire or no-fire call. Track B is a two-class segmentation over a 64 km patch, so it needs the usual reduction step (predicted burned area in km2, or a burned-or-not call on named neighbor cells).
- Dating and contamination: Item-level dating is exact, since every sample is a cell on a specific day. The published split is already a time holdout: 2006 to 2019 train, 2020 validation, 2021 to 2022 test, which is the structure Section 7.10 asks for as the comparison against a region holdout. Contamination: the dataset has been public since 2023 (arXiv 2023-06-08, NeurIPS 2023, Zenodo code v1.2 2023-06-14) and the coverage ends in September 2022, so everything sits before a 2026 model's cutoff. The negatives are sampled cells with no textual identity, which lowers the memorization risk relative to a named-fire task, but the positives correspond to real EFFIS-recorded Mediterranean fires.
- Build route: not needed
- Effort: One week, the lowest in this group. The ML tracks are already extracted, tabular, labeled, split, and paired with baselines, so the work is writing the sample-to-sentence converter and the scorer. Downloading only ml_tracks avoids the 648 GB cube entirely.

The negatives were sampled outside a 62 km buffer from any same-day ignition and matched to the land-cover distribution of the positives, so an item that exposes land cover gives the model a partial shortcut; that is an artifact of the sampling design and should be stated rather than engineered away. As with every pre-2022 source, there is no post-cutoff window, so this measures capability and not contamination resistance.
- Notes: If this group needs one forecasting task that can be standing up in a week, this is it. Mesogeos Track A is the only candidate here that arrives as a labeled, split, tabular classification set with published non-LLM baselines, which is exactly the comparison Section 7.5's "Non-LLM Baselines" bullet wants and exactly the comparison ramesh2025wildfiregpt made with TabNet. Its weakness is the mirror image of FireScope's: it gives a clean time holdout and no region holdout, and it ends in 2022, so it cannot supply post-cutoff items. Pairing Mesogeos Track A (time holdout, Mediterranean) with FireScope-Bench (region holdout, USA to Europe) would answer Section 7.10's holdout-type question with two real datasets rather than one.

### Incident-command transcript task-state monitoring

- Category and domain: Document Understanding, structure fire
- Verdict: **needs-work**
- Data: Source-grounded synthetic German firefighter incident-command scenarios released with the SwissText 2026 paper
- Page: https://github.com/zhaw-iwi/swisstext26_pub
- Access: public download, no registration. The repository is public, created 2026-05-05, last pushed 2026-05-07, about 21.7 MB. It holds the scenario JSON files, the dataset-generation and validation prompts, the source notes, the evaluation prompt payloads and the persisted request/response artifacts.
- License: The GitHub API reports the repository's license field as null, so there is no LICENSE file and no grant of reuse rights. The paper carries the ACL proceedings line "June 10, 2026 (c)2026 Association for Computational Linguistics"; the Anthology landing page did not render a per-paper license for me to read. Research use is implied by the release but redistribution of derived items is not licensed, so this needs an email to the ZHAW authors before we ship anything built on it.
- Size: Five German-language scenarios, 102 ordered radio messages, 15 predefined tasks, 15 task-state traces. Of the 15 tasks, all are explicitly assigned in the transcript evidence, 12 are completed within the scenario and 3 remain assigned but incomplete at scenario end.
- Reference answers: Yes, and in the best form of any item in this group. Each gold entry is a fixed-schema JSON tuple y(k) = (assigned, assigned_unit, completed, completion_outcome) over the current transcript prefix k, plus the message id at which assignment first becomes valid and, where applicable, the message id at which completion first becomes valid. Prefix-level gold states are derived deterministically from those transition annotations, and ambiguous transitions are resolved by explicit metadata rather than heuristics. Deterministic local checks enforce schema conformance, sequential message ids, exact alignment between predefined tasks and gold states, and consistency of the assignment and completion labels.
- Dating and contamination: Public since 2026-05-05, which is after the training cutoff of most models we would run, so verbatim contamination risk is genuinely low. The offsetting hazard is different in kind: the scenarios were generated and validated by gpt-5.4 through a 12-round generation, validation and revision loop, so evaluating any GPT-family model on them measures partial self-agreement rather than capability.
- Build route: Not needed for the released items, but the group's structure-fire coverage cannot lean on five scenarios. I searched for a public corpus of fire incident-command communication and found none. The nearest verified thing is RescueSpeech (arXiv 2306.04054), a German corpus of real speech from simulated search-and-rescue exercises involving firefighters, which is an ASR corpus with no task-state annotation; its HuggingFace page returned 401 so I could not confirm its license or hours. Radio corpora that do exist are police rather than fire and carry no task annotation. If we want a larger version of this task we would have to generate it, which reproduces the synthetic-data objection rather than answering it.
- Effort: Low to run as released: a day to wire the prefix-level evaluation, since the authors ship the pipeline. Two to three weeks if we extend it, which means scripting more scenarios against the same two Swiss source documents (Bundesamt fuer Bevoelkerungsschutz, Funkmaterial Sprechregeln, February 2004, and Feuerwehr Koordination Schweiz FKS, Reglement Einsatzfuehrung, November 2022) and re-running the validation loop with a non-GPT generator to break the self-agreement problem.
- Automatic scoring: Three of the four fields score exactly (two booleans and a unit string from a closed set). The fourth, completion_outcome, is a nullable free-text string capturing the reported completion result, so it needs normalization or a judge, and it is one of the two weaknesses the paper itself reports, alongside unit-assignment timing. Beyond that: 15 task traces give almost no statistical power, so any ranking across models will sit inside its own confidence interval; the transcripts are German, which confounds task ability with multilingual ability; and the authors state the scenarios are "cleaner and more linear than real firefighter radio traffic" and start from text rather than audio.
- Notes: Two corrections for the paper. First, the transcripts are not real: the paper is explicit that it evaluates "source-grounded synthetic firefighter scenarios", and describes the synthetic design as deliberate, because the research question needs the same operational content rendered under three transcript-structure conditions. The table's "Incident command transcripts; access unchecked" should say synthetic, released, five scenarios. Second, the table records the domain as "Not stated", but it can be settled from the dataset: the five scenarios are a kitchen fire in an apartment building, an underground-garage fire, a school basement fire, a workshop fire involving gas cylinders, and an attic fire in a row house. All five are structure fires, so this item counts toward structure-fire coverage. Answer to the question as asked: the released transcripts are synthetic and public, and no public corpus of real fire incident-command communication was found.

The most quotable IRPG content (LCES, the Standard Fire Orders, the 18 Watch Out Situations) is reproduced on hundreds of public pages and is almost certainly memorized. ### Multi-agent wildfire suppression and rescue

- Category and domain: Simulation-Coupled Agents, wildfire
- Verdict: **ready**
- Data: CREW-Wildfire, a procedurally generated wildfire response simulation benchmark with 12 scored levels, built on the CREW human-AI teaming platform and the Crew Dojo Unity framework. Four heterogeneous agent types (firefighters, bulldozers, drones, helicopters), partial observability, stochastic dynamics.
- Page: https://arxiv.org/abs/2507.05178
- Access: Public download. Code at https://github.com/generalroboticslab/CREW (39 stars, 16 commits on main); the wildfire component is at crew-algorithms/crew_algorithms/wildfire_alg with its own README naming the four frameworks implemented (CAMON, COELA, Embodied, HMAS-2). Documentation at https://generalroboticslab.github.io/wildfire-docs/. Published in TMLR 2025 (OpenReview 8mr27qFzKR). No registration or author request needed for the code. One friction point: the CREW install guide says the game environments "must be downloaded from a Google Drive folder and extracted to crew-dojo/Builds/", so the Unity builds sit outside version control and could move.
- License: Code repository: Apache-2.0. The arXiv posting of the paper carries CC BY-NC-ND 4.0, which forbids derivatives and commercial use of the paper text. Flag the mismatch rather than paper over it: we would build on the Apache-2.0 code, which permits research use and redistribution of derived items, and we would not redistribute the paper text. Note also that the abstract still reads "All code, environments, data, and baselines will be released" in the future tense while the repository is already populated, so the paper text lags the actual release.
- Size: 12 benchmark levels across 16 level configurations. Team compositions range from 2 to 12 agents per level (for example "10 F, 1 B, 2 D, 2 H" for the Full Environment level). The environment scales to "2000+ agents and 1 million+ cell maps", with 1000x1000 cells as the standard large test configuration. The published experiment set is 410 trajectories: 3 to 10 random seeds on all 16 configurations, on GPT-4o at temperature 0.
- Reference answers: Yes, and of the right kind for this group. The simulator computes the score, so no human is in the loop and no rubric is needed. Each level has an explicit score function: Cut Trees (sparse and lines, small and large) scores trees cut in labeled cells; Scout Fire scores drones over fire, max 2; Transport Firefighters scores firefighters at target; Rescue Civilians (known location, search and rescue, search plus rescue plus transport) scores civilians rescued; the four Suppress Fire levels score "Trees Destroyed + 20x Agents Lost"; Full Environment scores "Trees Destroyed + 20x Agents Lost + 100x Civilians Lost". The paper also logs task success, task duration, API call frequency and input/output token usage.
- Dating and contamination: Scenarios are procedurally generated, so the specific instances we evaluate on did not exist before we generate them. This is the lowest contamination risk of the five items. The residual risk is that a model has read the public repository, its prompt templates and the paper, which shapes strategy rather than supplying answers. The code has been public since 2025 (arXiv v1 2025-07-07, v2 2025-12-12), so a 2026 model may well have seen it; regenerating maps with fresh seeds removes the instance-level risk entirely.
- Build route: not needed. The environment and the scoring are released.
- Effort: About one week to stand up, then the token budget. Install is heavier than a pip command: conda for the base environment, Poetry for crew-algorithms, Go v1.18, Docker Desktop for the Nakama networking service, and the Unity game builds from Google Drive into crew-dojo/Builds/. Hardware is modest; the paper reports "Experiments were conducted on a laptop with a 3.0 GHz CPU, RTX 3060 GPU, and 16GB RAM", and the large configuration wants a desktop with 16GB GPU and 16GB RAM. The dominant cost is LLM tokens. The paper says "Our current experiments are limited by the relatively high costs associated with LLM token usage" and gives no dollar figure, which is itself a gap; every agent in a 2 to 12 agent team is issued calls over a long horizon, so budget a pilot run on one small level to measure tokens per trajectory before committing to a full sweep across several models and conditions.
- Automatic scoring: Scoring is mechanical, but three things complicate the comparison. Stochastic dynamics and partial observability mean a single seed is noise; the paper itself runs 3 to 10 seeds per configuration, so our protocol has to fix a seed count and report variance rather than a point estimate. Scores are unbounded penalty sums on different scales per level (trees destroyed, civilians lost, drones on target), so aggregating across the 12 levels needs a normalization choice we have to defend. And the reference point matters: several frameworks scored below the Do-Nothing baseline on the hard levels, so a Do-Nothing column has to sit beside every number or a ranking of failures reads as a ranking of successes.
- Notes: This is the strongest of the five by a wide margin, and the only one I would call ready. Permissive code license, keys computed by the simulator, procedural generation that defeats memorization, and modest hardware. The two open questions are operational rather than evidentiary: what a full sweep costs in tokens, and whether the Google Drive Unity builds stay available. Both are worth resolving with a pilot run before the task is written into the paper as committed. One caution on positioning: the published result is that four multi-agent frameworks on GPT-4o broke down on large-scale suppression and rescue, often underperforming Do-Nothing. That makes the levels a good discriminator today and a poor one if frontier models saturate the easy levels, so plan to report per-level scores rather than one aggregate.
- Evidence: https://arxiv.org/abs/2507.05178, https://arxiv.org/html/2507.05178v2, https://github.com/generalroboticslab/CREW, https://github.com/generalroboticslab/CREW/tree/main/crew-algorithms/crew_algorithms/wildfire_alg, https://generalroboticslab.github.io/wildfire-docs/, https://generalroboticslab.github.io/crew-docs/, https://generalroboticslab.github.io/crew-docs/getting_started/install.html, https://mlanthology.org/tmlr/2025/hyun2025tmlr-crewwildfire/

### Policy adaptation as the set of agents and tasks changes

- Category and domain: Simulation-Coupled Agents, wildfire
- Verdict: **needs-work**
- Data: The MOASEI wildfire track runs on free-range-zoo, a PyTorch multi-agent environment suite with wildfire, rideshare and cybersecurity domains, built for agent, task and frame openness. The wildfire domain is a grid world in which fires spread and agents spend and replenish suppressant; MOASEI 2026 used 3x3 grids (wildfire_0, wildfire_1, wildfire_2) plus a bonus frame-openness scenario.
- Page: https://arxiv.org/abs/2507.05469
- Access: Public download. Environment at https://github.com/oasys-mas/free-range-zoo (9 stars, 625 commits), with a frozen evaluation release tagged moasei2026v1.0 dated 2026-01-05, described as "the frozen version of free-range-zoo which will be used to evaluate results". Starter kit at https://github.com/oasys-mas/moasei-starter. Competition training configurations are published as a Kaggle dataset linked from https://oasys-mas.github.io/moasei.html; I could not read the Kaggle page (JavaScript-rendered) so I cannot confirm whether a Kaggle account is required, and I have recorded that URL as a failed fetch. The environment itself needs no such account.
- License: free-range-zoo: MIT, which permits research use and redistribution of derived items. moasei-starter: AGPL-3.0, which is copyleft and would require source release if we distributed a derived starter, so prefer building against free-range-zoo directly. The 2025 technical report is CC BY 4.0.
- Size: Three wildfire scenarios plus a bonus, on 3x3 grids with varying initial fire positions and agent placements. The 2025 evaluation used three configurations (WS1, WS2, WS3) of increasing openness with n=256 independent simulation runs per policy, fixed random seeds and consistent scenario generation. Observation space is a TensorDict of self <ypos, xpos, power, suppressant, range, capacity, equipment>, others (the same fields, partially observed), and tasks <y, x, fire level, intensity>. Action space is discrete and stochastic, [fight_0, ..., fight_tasks, noop (-1)].
- Reference answers: Yes, computed by the simulator. The 2025 report uses "average cumulative episodic reward of multiple runs as the primary performance metric across all tracks", with significance at p<0.05. The 2026 edition "expanded its reporting metrics to emphasize total task completions, mean task-completion time, and mean value of completed tasks". Four reference policies ship with the wildfire environment: noop, random, strongest (fight the highest-intensity fires) and weakest (fight the fires closest to going out). No human judge is needed. The documented specification page does not state the reward function terms, so those have to be read out of the code.
- Dating and contamination: Configurations are drawn from a distribution and the 2026 held-out test set is "drawn from the same distribution but are not guaranteed to be identical to the training set", so instance-level contamination is low, as with CREW-Wildfire. The frozen evaluation release is dated 2026-01-05 and the repository has been public since before the 2025 competition, so a 2026 model may have read the code. Regenerating configurations with fresh seeds removes the instance risk.
- Build route: not needed for the environment. The LLM-in-the-loop harness does need building; see effort.
- Effort: About 1 to 2 weeks. Install is straightforward (Python 3.12, Rust/Cargo, Poetry). The bulk of the work is a decision-time wrapper that renders the TensorDict observation into a prompt and maps a model's reply back onto the discrete action list, because MOASEI itself never ran an LLM in the loop and no such wrapper exists in the repository. Budget a discrimination check at several values of n before committing, for the reason in the scoring column.
- Automatic scoring: The reward is mechanical but it does not separate policies well. The 2025 wildfire results were University of Tehran (CNN) 11.41 plus or minus 0.63, Markov Mayhem (GNN) 11.36 plus or minus 0.61, BIT Student (LLM-driven) 7.71 plus or minus 0.27, and the "Smallest" heuristic baseline 11.35 plus or minus 0.57; the top two matched the baseline with no statistically significant difference at n=256. A benchmark whose metric cannot distinguish a graph neural network from a one-line heuristic will not distinguish two frontier models either, so this task needs harder configurations, many more runs, or a metric that separates better before it earns a place. The reward terms are also undocumented on the public specification page, which is a reproducibility problem for a TMLR reader who wants to check the scoring.
- Notes: Two findings change how this item should be written up, and both contradict the current framing. First, the LLM in MOASEI is not an agent. The report says the BIT Student team "adopts a meta-optimization loop in which an LLM (e.g., GPT-like architecture) generated policy modifications by analyzing past performance, then injected the modified strategy into the environment for further testing". The model writes and revises a policy offline between episodes; the thing acting in the environment is that policy. So the work does not measure an LLM making wildfire decisions, and Section 7 of the outline should carry that qualifier wherever patino2025moasei is cited as evidence about agents. Second, the 2026 competition rules state that "during official evaluation runs, agents must operate without the use of any LLMs". That is a competition rule and not a restriction on the MIT-licensed environment, so it does not block us, but it does mean the MOASEI leaderboard will never produce LLM numbers to place beside ours. A third point for the paper: the wildfire domain here is a 3x3 grid abstraction, so a score on it measures coordination under openness rather than fire decision-making, and the item should be described that way. A second edition exists (arXiv:2607.03399, submitted 2026-07-03) if the outline wants the more recent citation.

- Category and domain: Detection and Perception, candidate data source, wildfire
- Verdict: **ready**
- Data: FIgLib, the HPWREN Fire Ignition images Library: sequences of wildland fire images from fixed field-of-view cameras at HPWREN mountaintop sites in Southern California, each sequence spanning roughly 40 minutes before and 40 minutes after a single ignition.
- Page: https://www.hpwren.ucsd.edu/HPWREN-FIgLib/
- Access: Public download, no registration, no request. Direct HTTP from https://cdn.hpwren.ucsd.edu/HPWREN-FIgLib-Data/index.html , which lists per-sequence directories of JPEGs plus an MP4 time-lapse, with whole sequences also available as tgz archives under a Tar/ directory. Bounding-box labels are at .../Miscellaneous/Labels/HPWREN-BB/ in CSV and Pascal VOC XML, alongside the labelem.py annotation tool. Contact for questions and for an update-announcement list: fback@hpwren.ucsd.edu.
- License: No formal license. Two sentences govern use: "This data is provided as-is, no guarantees for anything is included" and "While we are making the data publicly available, its use requires a credit reference to https://www.hpwren.ucsd.edu/ in derivative work." Read plainly, that permits research use and permits releasing derived items such as questions built from the images, on condition of crediting HPWREN. It does not explicitly grant redistribution of the images themselves, so a derived benchmark should ship item identifiers, labels and a download script rather than the JPEGs. HPWREN also asks users to say what they are using it for, which is worth doing.
- Size: Roughly 30 GB as of July 2024 per the page, growing. We counted 453 distinct dated sequences in the current index (the page says "more than 400"); the 2022 paper's snapshot was 315 sequences from 101 cameras across 30 stations, 24,800 images at 1536x2048 or 2048x3072, typically 81 frames per sequence at about 60-second spacing. Public bounding-box label sets cover 9 sequences.
- Reference answers: Yes, and free. Image file names are origin_timestamp_offset-in-seconds-from-visible-plume-appearance.jpg (for example 1720453551_-02400.jpg, 1720455951_+00000.jpg, 1720458232_+02281.jpg), so the sign of the offset is a per-image binary smoke/no-smoke label with no annotation work at all, and the magnitude gives a direct time-to-detection metric. Roughly half of each sequence is negative by construction. Box labels exist for 9 sequences in CSV and VOC XML. Contour masks are not published. The 2022 paper records a richer annotation set covering 144 fires with boxes and contour masks and lists its release as future work: "upon further validation, releasing the human-annotated bounding boxes and contour masks".
- Dating and contamination: Every item dates itself. Directory names are YYYYMMDD_firename_camera, for example 20170708_Whittier_syp-n-mobo-m. Current range runs 2016-06-04 to 2026-09-09, with per-year counts of 14 (2016), 41 (2017), 66 (2018), 89 (2019), 91 (2020), 12 (2021), 61 (2024), 50 (2025) and 29 (2026). The 79 sequences from 2025 and 2026, roughly 6,400 images, postdate the training cutoff of every model we would evaluate, and new sequences arrive continuously (the newest is nine days old). FIgLib as a corpus has been public since 2020-08-18 and heavily cited since 2022, so pre-2022 sequences carry real contamination risk while the recent slice does not. This is the only source in the whole group that solves contamination by construction rather than by argument.
- Build route: Not needed; this is itself the build route for item 2 above and a natural home for the outline's post-cutoff-items bullet in 7.8. Concretely: crawl the 2025 and 2026 sequence directories, parse the offset from each file name, sample a balanced set stratified by camera, time of day and offset bucket, and score binary presence plus the earliest offset at which a model first says yes.
- Effort: About 3 to 4 person-days for a dated binary and time-to-detection task, most of it a polite crawl and a file-name parser. Add 2 to 3 weeks if we want localization labels, using HPWREN's own labelem.py on a sampled slice, or an unknown wait if we request the 144-fire annotations instead.
- Automatic scoring: Binary answers score exactly. Two honest difficulties. Early frames just after the plume appears are genuinely ambiguous, and the 2022 paper records 1,213 positive images, about 20 percent, whose contour annotations are missing partly because the smoke is hard to see, so the label near offset zero is noisier than the file name suggests; scoring by offset bucket rather than pooling all positives handles this. Separately, the corpus is about 50 percent positive by construction and the paper itself flags that this "is not representative of real-world scenarios", so a false-positive rate on the 2025 and 2026 negatives should be reported beside accuracy.
- Notes: Yes, questions with reference answers can be built from these images, and more cheaply than from any other source checked. The 7.7 data-sources bullet calling FIgLib "a publicly available dataset used for smoke detection" is confirmed, and the citation for that claim should be the HPWREN page and the Dewangan et al. paper rather than seidel2025forestfirevlm, which only reports using it. Two corrections for the outline text: FIgLib has a credit-reference condition rather than a license, which the data-sources subsection should say plainly; and only 9 sequences have public boxes, which is what constrains item 2. The dating property deserves its own mention in 7.8, since "test items built from fire events and records dated after each model's training cutoff" currently reads as an aspiration and this source makes it concrete. Our first fetch of hpwren.ucsd.edu/FIgLib/ redirected to legacy-www.hpwren.ucsd.edu, whose TLS certificate has expired; the working entry point is the HPWREN-FIgLib path given above.

### Source check: DetectiumFire as a basis for fire-scene perception and risk-severity items

- Category and domain: Detection and Perception, candidate data source, both (indoor and structure fire dominate the labeled taxonomy: 3,374 indoor images and 4,175 outdoor, of which forest and wildfire account for 1,045 and house or residential fires for 1,159)
- Verdict: **not-feasible-now**
- Data: DetectiumFire, a multimodal fire-understanding dataset from Tulane University with Aalto University, NeurIPS 2025 Datasets and Benchmarks track.
- Page: https://www.kaggle.com/datasets/38b79c344bdfc55d1eed3d22fbaa9c31fad45e27edbbe9e3c529d6e5c4f93890
- Access: Public download on Kaggle behind a free account. The Kaggle distribution record marks the zip download "requiresSubscription": true, which in Kaggle's schema means a signed-in user. Code and metadata at https://github.com/ZixuanLiu4869/DetectiumFire (created 2025-10-21, no LICENSE file, 568 KB); models at https://www.kaggle.com/models/yimengfuyao/detectiumfire-models .
- License: This is the blocker, and the two authoritative sources disagree. The arXiv paper states "License: CC BY-NC-SA 4.0". The Kaggle page, which is where the data is actually distributed, records "Attribution-NonCommercial-NoDerivatives 4.0 International (CC BY-NC-ND 4.0)". The NoDerivatives term forbids distributing adapted material, so under the Kaggle license we could evaluate models against it privately but could not release a derived question set, which is exactly what a TMLR benchmark artifact requires. The paper adds a second restriction independent of the license: "Notice that most part of our real-world data was collected via public web search. In accordance with standard academic practice and ethical use guidelines, these data should be restricted to academic use only", and it acknowledges that web sourcing "may impose legal or ethical restrictions on downstream usage". Source data licenses are mixed and listed in the paper's Appendix B.1, including CC BY-NC-SA for the web-search and IoT portions and CC BY 4.0 for one component.
- Size: 22.5k fire-related images (14.5k real-world plus 8k synthetic) and 2.5k videos. The curated annotated core is 7k fire images with 7k deliberately hard non-fire images, and 1.7k fire video clips of at least 10 seconds plus 757 non-fire clips. The scenario taxonomy covers 7,549 labeled images. A preference dataset of 12k labeled pairs supports generative-model work that is out of scope for us.
- Reference answers: Partly, and none of it is question-shaped. What exists: YOLO-format bounding boxes made on Roboflow by human annotators over several months, with inter-annotator agreement reported in Appendix B.2; captions capped at 75 tokens covering what is burning, the surrounding environment, and fire severity; and a four-level risk taxonomy of No Risk, Low Risk, Moderate Risk and High Risk. The severity labels are the usable reference answers for a scored classification item, and the authors' own reasoning experiment reports severity-classification accuracy rising from 56.06 to 83.84 percent after fine-tuning. What does not exist: any question and answer pairs. The authors evaluated free-text attribute predictions by using GPT-4o "to evaluate whether the model's outputs matched the ground-truth attributes derived from our human-verified captions", that is, a judge model rather than a fixed key.
- Dating and contamination: Items cannot be dated. The images were scraped from Google, Twitter, YouTube and TikTok plus some IoT capture during controlled demonstrations, and no capture dates, source URLs or acquisition window are recorded in the paper. The Kaggle record's dateModified is 2025-10-22 and the arXiv preprint is 2025-11-04. Because the images were public on social platforms before collection, a 2026 model may well have seen them long before DetectiumFire existed, and there is no way to test that without per-image provenance. This is the weakest contamination story of the four NeurIPS entries.
- Build route: If we want the severity-reasoning idea without the license problem, build it elsewhere. For structure fire, Fire360 (row below) has expert-verified labels and a research-use license. For wildfire severity, FIgLib gives dated imagery and free binary labels but no severity scale. Within DetectiumFire itself the only compliant route is to seek written permission from the authors to redistribute a derived question set, since the ND term otherwise controls, and to ask them to reconcile the arXiv and Kaggle license statements.
- Effort: Low if only used internally: about 2 days to download, subset to the 1,045 forest and wildfire plus 1,159 residential images, and turn the four-level risk taxonomy into a multiple-choice item with the severity label as the key. High if a public release is wanted: an author permission round with no guaranteed outcome, which is why the verdict is what it is.
- Automatic scoring: A four-way severity multiple-choice item scores by exact match and is clean. Everything else is harder: the captions are free text capped at 75 tokens and were themselves scored by GPT-4o against human-verified captions in the source paper, which reintroduces a judge dependency. The risk taxonomy is also somewhat subjective at the boundaries (a controlled campfire against an uncontrolled outdoor fire), so inter-annotator agreement should be quoted beside any score.
- Notes: Questions could be built from these images, and the four-level risk taxonomy would give them reference answers, but the license as published on the distribution page forbids releasing them. The license discrepancy is the single most consequential finding on this row and should be raised with the authors before the paper cites either value: arXiv says CC BY-NC-SA 4.0, Kaggle says CC BY-NC-ND 4.0, and only the latter governs what a downloader receives. Note also that 8k of the 22.5k images are diffusion-generated, so any subset we sample must exclude synthetic_images/ for a perception claim about real scenes. Our two attempts on the OpenReview forum and camera-ready PDF both returned a Cloudflare browser-verification page, so the venue and license facts above come from the arXiv copy and the Kaggle record rather than from OpenReview.
- Evidence: https://arxiv.org/abs/2511.02495, https://arxiv.org/html/2511.02495, https://arxiv.org/pdf/2511.02495, https://www.kaggle.com/datasets/38b79c344bdfc55d1eed3d22fbaa9c31fad45e27edbbe9e3c529d6e5c4f93890, https://api.github.com/repos/ZixuanLiu4869/DetectiumFire, https://openreview.net/forum?id=vhHYTjMt9Z, https://openreview.net/pdf/4eeb3b9037ca4510434700dcd23105ef77257806.pdf

### Source check: Fire360 as a basis for structure-fire perception and safety-reasoning items

- Category and domain: Detection and Perception, candidate data source, structure fire (firefighter training drills; 43.9 percent indoor, 56.1 percent outdoor suppression; no wildfire content)
- Verdict: **needs-work**
- Data: Fire360, a benchmark of degraded 360-degree firefighting training video, NeurIPS 2025 Datasets and Benchmarks track.
- Page: https://arxiv.org/abs/2506.02167
- Access: Public download, no login. The dataset is hosted at https://uofi.box.com/v/fire360dataset , a University of Illinois Box shared link that resolves to uofi.app.box.com and returns HTTP 200 with public shared-item metadata. The paper notes the hosting choice and what ships with it: "We release the dataset, annotation toolkit, and benchmark suite publicly under a version-controlled, research-only license. Videos are hosted via Box ... with documentation, metadata (Croissant schema), and contact instructions provided."
- License: "Fire360 is released under a research-only MIT license with added restrictions that prohibit use in surveillance, enforcement, behavioral profiling, or nonconsensual monitoring contexts." That is a custom restricted license rather than MIT, despite the name. Academic benchmark use falls inside the stated intent, and "research-only" plus the toolkit release implies derived research items are acceptable, but the wording is bespoke enough that we should confirm the exact LICENSE text in the Box folder before releasing derived items and should quote the restriction in our data statement. The arXiv preprint is CC BY 4.0.
- Size: 228 professionally recorded 360-degree videos, 180,000 seconds (50 hours), captured on a Ricoh Theta V at 3840x1920 and 60 fps, stitched to equirectangular panoramas. Splits are 137 training, 45 validation and 46 test videos, stratified by scene type, lighting and procedural diversity, with the test set enriched for high degradation. Lighting mix: 63 day, 65 night, 100 mixed.
- Reference answers: Yes, expert-verified, with human baselines, which is rare in this group. Annotations: 348 temporal action instances across 8 categories; spatial bounding boxes averaging 5.7 objects per video; environmental tags including a 1 to 5 smoke grade; 100 VQA questions split evenly between multiple-choice and free text; 154 Transformed Object Retrieval targets across 87 keyframes against 50 pristine exemplars in 20 categories; and safety-reasoning checklists. Labels were made by the dataset creator and verified by two certified fire safety researchers, with inter-annotator agreement of 0.87 for actions, 0.91 for objects and 0.85 in high-smoke scenes; a 15 percent subset re-annotated by external instructors reached 93.7 percent confirmation. Metrics are fixed: exact-match accuracy for VQA, BLEU-4 for temporal captioning, mean IoU for localization, binary checklist accuracy for safety reasoning, top-1 accuracy at IoU at least 0.5 for retrieval. Human baselines are published: 91.4 percent VQA overall and above 80 percent in all conditions, 0.85 captioning agreement, 94.6 percent safety checklist, 83.5 percent on retrieval.
- Dating and contamination: Items cannot be dated precisely. The paper says recordings span summer and winter sessions at one North American firefighter training institute and gives no calendar dates. Public since the arXiv posting on 2025-06-02 and the NeurIPS 2025 D&B presentation, so roughly fifteen months of exposure. Because the content is training-drill video from a single institute rather than widely circulated web media, incidental pretraining exposure is less likely than for the scraped corpora, but the released annotations and the 100 VQA questions have been on a public Box link for over a year and could have been ingested.
- Build route: Not needed for access; needed for scale. The limiting number is 100 VQA questions, which is too few to separate models with confidence, and 50 of those are free text. The extension route is documented and cheap: the authors ship the browser-based annotation tool and say "the interface supports extensibility: users can define and annotate custom classes", and 228 videos at 50 hours leave ample unlabeled material. Writing an additional 300 to 500 multiple-choice items over the existing action and object annotations, and validating them with a fire protection engineer, would turn this into a usable structure-fire task. Note that this is the same expert pool the outline's 7.7 human-baseline subsection would need anyway, so the two can be scheduled together.
- Effort: About 1 to 2 weeks to use the 100 existing VQA items plus the safety checklists as shipped, mostly pulling 50 hours of 360-degree video and building the equirectangular-to-rectilinear preprocessing the paper shows matters (rectilinear projection lifted GPT-4o VQA and Grounding DINO IoU in every condition tested). About 4 to 6 weeks including an item-writing round with a fire protection engineer to reach a defensible item count.
- Automatic scoring: Three difficulties, all named in the paper. BLEU-4 on 348 captions is a weak metric for domain language and the authors concede as much ("we acknowledge its limitations for domain-specific language"). The 50 free-text VQA items need a matcher; only the 50 multiple-choice items score cleanly by exact match. Safety-reasoning scoring is "conducted via checklist comparison validated by certified instructors", so the checklists must come out of the Box folder in machine-readable form or that task is not automatable. Localization on equirectangular frames also carries projection error: the paper reports about 15 percent of 360-degree boxes are misaligned by projection distortion, which sets a ceiling on IoU scores.
- Notes: Yes, questions with reference answers exist and more can be built. This is the best structure-fire perception source we checked, and it is the only candidate in the whole group that ships published human expert baselines, which the outline's 7.7 subsection currently lists as an open access-plan problem. It also directly supports the 7.9 sensitivity bullet on input representation, since the paper measures the same models under equirectangular and rectilinear projections and finds the ranking shifts. The domain-coverage criterion in 7.2 asks whether the chosen tasks together cover both fire domains; Fire360 is currently the strongest way to satisfy the structure-fire half on perception, with FIgLib or WildFireVQA covering wildfire. Its weakness is scale, not access. One caution on the 7.3 table: the outline has no Fire360 row yet, and adding one would need a citation key, since the context pack notes that none of the three NeurIPS 2025 entries has one.

### Source check: RSCC as a basis for post-fire change and burn-scar perception items

- Category and domain: Detection and Perception, candidate data source, wildfire (post-event only; 5 of 31 events are wildfire, all pre/post damage rather than active fire)
- Verdict: **not-feasible-now**
- Data: RSCC, Remote Sensing Change Caption dataset for disaster events, NeurIPS 2025 Datasets and Benchmarks track. Built by cropping and captioning xBD and EBD imagery, both from the MAXAR Open Data Program.
- Page: https://huggingface.co/datasets/BiliSakura/RSCC
- Access: Public download, not gated. Hugging Face record: gated false, private false, created 2025-04-22, last modified 2026-02-14, 347 downloads, size category 10K to 100K. Code and a Google Drive subset at https://github.com/Bili-Sakura/RSCC , project page at https://bili-sakura.github.io/RSCC/ , Croissant metadata published. The repository adds a condition: "The user should strictly obey the xBD License. Also, we (RSCC Team) highlight the distribution of this subset data is for research purpose only."
- License: Declared CC-BY-4.0, on the Hugging Face card and in the paper's own data-license section: "The dataset is released under the [CC-BY-4.0], which permits unrestricted use, distribution, and reproduction in any medium, provided the original work is properly cited." That declaration sits uneasily beside the repository's own instruction to obey the xBD license and its research-purpose-only restriction, since a CC BY 4.0 grant and a research-only restriction cannot both govern the same bytes. The paper says source licenses for MAXAR OpenData "are stated in Appendix A" and cites xBD and EBD properly. Before relying on CC BY 4.0 for a derived release we should check the xBD terms directly, which we did not do in this pass.
- Size: 62,351 bi-temporal pre/post image pairs at 512x512 (xBD 44,136 cropped without overlap from 1024x1024, EBD 18,215 native), across 31 global events. Splits: train 61,363 pairs over 31 events, test 988 pairs over 19 xBD events. Distribution on Hugging Face is a tarball split into five parts plus RSCC_qvq.jsonl and conversion scripts.
- Reference answers: Yes in form, no in substance, and this is the reason for the verdict. The reference change captions were generated by a model, not written by people: "we call QvQ-Max (qvq-max-2025-03-25) API from Alibaba Cloud to automatically generate annotations", followed by an automated post-correction pass with Qwen2.5-Max that forces agreement with xBD metadata, then manual validation of a 10 percent sample by three experts against a binary rubric. Scoring a model against these captions measures agreement with QvQ-Max plus a metadata filter. The paper's own human preference study makes the circularity visible: it reports QvQ-Max, labelled there as the ground truth, winning 80.7 to 99.0 percent of head-to-head votes against every baseline. The real human labels sit one layer down, in xBD's building bounding boxes with Joint Damage Scale damage levels, which are human-annotated.
- Dating and contamination: Events are dated precisely in the paper's Appendix A table. The 5 wildfire events are Portugal wildfires (17 to 24 June 2017), Santa Rosa wildfires (8 to 31 October 2017), Carr wildfire (23 July to 30 August 2018), Woolsey fire (9 to 28 November 2018) and Pinery fire (25 November to 2 December 2018). Per-event pair counts are not given in the table we extracted. All five are seven to nine years old, xBD has been a standard public benchmark since 2019, and RSCC itself has been on Hugging Face since 2025-04-22 with 347 downloads. Contamination risk is high on both the imagery and the underlying damage labels for any 2026 model.
- Build route: Skip RSCC and go to the layer beneath it. xBD provides human building bounding boxes with Joint Damage Scale labels, described in the RSCC paper as "human annotations of building bounding boxes with damage assessment labels ... developed with contributions from organizations such as NASA and the California Air National Guard". A damage-level multiple-choice item over the 5 wildfire events, keyed to those human labels, is scorable by exact match and does not depend on any model-written text. That requires fetching and checking xBD's own distribution and license, which this pass did not cover. RSCC's contribution over xBD is the captions, and the captions are the part we cannot use.
- Effort: About 1 week to build a damage-level item set from xBD's wildfire events once its license and download are verified, plus the license check itself. Using RSCC captions as they stand is fast but would not survive review, so the effort estimate for the usable version is the xBD route.
- Automatic scoring: Caption scoring is the problem and the authors say so. The reported metrics are ROUGE, METEOR, BERTScore and ST5-SCS, and the paper writes of an additional learned metric that "the BLEURT is strongly biased on text length, which fails in valid evaluation. We are seeking for more reliable metrics in the future." Overlap metrics against a single model-written reference reward stylistic imitation of QvQ-Max rather than correctness. A damage-level multiple-choice reformulation over the xBD labels avoids all of this.
- Notes: Questions can be built from these images, but not with RSCC's own reference answers, because those answers are another model's output. For a TMLR paper whose stated criterion in 7.2 is "a reference answer or expert label for every test item", model-written captions do not meet the bar, and a reviewer would reasonably ask what a score against QvQ-Max output means. The wildfire slice is also small and old: 5 of 31 events, all 2017 and 2018, none more recent, so it fails the contamination-control criterion as well. If the outline wants a post-wildfire burn-scar and damage row, the geospatial-analysis entry citing lahouel2026iceo is the better anchor and xBD is the better data layer. Note that RSCC's relevance here is to post-event damage, not to the active-fire perception the other five items address, so dropping it costs the design little.
